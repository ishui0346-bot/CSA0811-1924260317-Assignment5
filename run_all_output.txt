                 | robust: OK: 1 rows (delimiter=',', encoding=latin-1)
utf16_encoding   | naive: CRASH UnicodeDecodeError: 'utf-8' codec can't decode byte 0xff in position 0: invalid 
                 | robust: OK: 2 rows (delimiter=',', encoding=utf-16)
empty            | naive: no crash, 0 rows (silent!)
                 | robust: REJECTED: file is empty

====================================================================== 
2. SQL: string concatenation (+) vs ? placeholder
======================================================================
concat  | input="O'Brien Nagar"
        | SQL sent: SELECT ... WHERE station = 'O'Brien Nagar'
        | ERROR: OperationalError: near "Brien": syntax error
param ? | input="O'Brien Nagar"
        | result: 70.0

concat  | input="Adyar' OR '1'='1"
        | SQL sent: SELECT AVG(pm25) FROM aq WHERE station = 'Adyar' OR '1'='1'
        | result: 71.0
param ? | input="Adyar' OR '1'='1"
        | result: None

Explanation: with +, the quote in the data closes the SQL string early. 'O'Brien Nagar' becomes a syntax error, and  Adyar' OR '1'='1  becomes the condition  station='Adyar' OR '1'='1'  which is always true, so ALL rows are averaged (injection). With ?, the value is passed separately from the SQL text and is always treated as data: the quote is harmless and the injection matches no station (None).

====================================================================== 
3. executemany() vs execute() in a loop (on-disk database, one commit)
======================================================================
n=  1,000 | execute loop 0.0025s | executemany 0.0016s | ratio 1.62x
n= 10,000 | execute loop 0.0182s | executemany 0.0116s | ratio 1.56x
n=100,000 | execute loop 0.1256s | executemany 0.0768s | ratio 1.64x
n=200,000 | execute loop 0.2210s | executemany 0.1560s | ratio 1.42x
Both are O(n); executemany keeps the loop in C and prepares the statement once, so the constant is smaller. (Real gain is larger if commit() is called inside the loop: n disk syncs instead of 1.)

==================================================================
5. WHAT EACH ADVERSARIAL INPUT REVEALS ABOUT THE DESIGN
==================================================================
- Missing column / empty file : the naive loader either crashes later (KeyError) or silently returns nothing.
  Design lesson: validate the header and file size BEFORE processing and report a clear reason.
- Wrong delimiter             : the header becomes ONE column named 'station;date;hour;pm25'. Without detection every
  value would be treated as missing. Lesson: sniff the dialect and check required columns.
- Different encoding          : UTF-8 assumption raises UnicodeDecodeError (latin-1 / utf-16 files). Lesson: detect BOM,
  try encodings in a defined order, and log which one was used.
- Quote in a station name     : string building is not just an inconvenience, it is a security hole. Lesson: always
  use ? placeholders; never trust text from files, apps or users.
- Sarcasm / double negatives / mixed opinions : a word-list scorer has no understanding of context, tone or scope.
  Lesson: treat the score as a rough signal, measure agreement with human labels (B4), and use a trained model
  (or human review) where accuracy matters.

## B4.1b Summariser (frequent-word sentences) vs first-k sentences (k = 1)

Quality measure = share of the complaint's 4 most frequent content words that appear in the summary.

- frequent-word summariser: mean coverage **92%**
- first-k baseline:         mean coverage **99%**
- frequent-word better on 0 complaints, equal on 47, worse on 4.
- the two methods choose a DIFFERENT sentence for 5 of 51 complaints.

Example complaint:
> I love the new bus lanes. Traffic is better and the air feels clean. Keep going.

- frequent-word: ['Traffic is better and the air feels clean.']
- first-k: ['I love the new bus lanes.']

Note: complaints are short (2-3 sentences) and rarely repeat a word, so the frequency score mostly favours the longest sentence, which is often the first one. The frequent-word method pays off on longer, rambling complaints where the main issue is repeated; for short ones first-k is almost as good and cheaper.

Time per complaint: sentiment scorer 3.0 µs, frequent-word summary 10.1 µs, first-k 1.5 µs.  (first-k needs only the first sentence boundary, ~O(1)-ish in practice; frequent-word is O(words); space O(words) for the Counter vs O(1) extra.)

At 50,000 complaints a month the scorer needs about 0.15 s and the summariser 0.51 s per month: computing time is not a concern.

## B4.2 Effect of an index on (station, day)

Table size: 1,051,200 rows (120 stations x 365 days x 24 readings); loaded in 1.18 s (893,791 rows/s).

Query: `SELECT AVG(pm25) FROM aq WHERE station = ? AND day BETWEEN ? AND ?` (average of one station for one month)

- before index: **34.26 ms** per query; plan: `SCAN aq`
- after index:  **0.075 ms** per query; plan: `SEARCH aq USING INDEX idx_station_day (station=? AND day>? AND day<?)`
- speed-up: **458x**; building the index took 0.40 s once (and adds extra disk space and slightly slower inserts).

## B4.3 Production decision (justified with the measurements above)

Scale: (12 + 100) stations x 96 readings/day x 365 = **3,924,480 readings/year** (about 3.7x the
table tested above) and 50,000 complaints/month.

**Storage.** Keep a relational database. SQLite (with `?` placeholders, `executemany`, and the (station, day) index) handled
1,051,200 rows with one-month queries in 0.07 ms. At ~3.9 M rows/year a single file is still
possible for a single writer, but 112 stations writing every 15 minutes, plus dashboards reading at the same time, suggests a
server database (PostgreSQL, optionally partitioned by month) for concurrent writers and backups. The schema from A1 stays the same.

**Cleaning.** Clean each station file incrementally when it arrives (a daily or 15-minute batch) instead of re-reading history.
Use pandas/vectorised cleaning for batches (B1 measured about 5-6x faster than loops at 1,000,000 rows) and keep the same
rules, plus the input validation from B2 (header, delimiter, encoding, empty file). Keep raw files unchanged for audit.

**Analysis.** Daily and monthly summaries by SQL GROUP BY on indexed data (B3: all methods are O(n) but SQL avoids reloading
history); pandas only for ad-hoc analysis and charts.

**AI methods.** The word-list scorer and extractive summariser cost about 3 µs and 10 µs per complaint,
so 50,000 complaints are processed in seconds. But the scorer agreed with my labels on 84% of 51
complaints (an optimistic figure: the lexicon was extended while I was reading these same complaints, so on new data it will be lower), and B2 showed systematic failures (sarcasm, double negatives, mixed opinions). Decision: use the lexicon scorer only as
a cheap first filter (e.g. routing obviously negative complaints), and train/fine-tune a small supervised model (e.g. Naive Bayes
or logistic regression on TF-IDF, or a pre-trained language model) on human-labelled complaints for the reported sentiment. Compute
is not the obstacle; accuracy is. Re-measure agreement on a larger labelled sample before and after switching.
